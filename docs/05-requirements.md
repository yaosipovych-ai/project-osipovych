# ЗВІТ 
**з практичної роботи № 5**
**Тема:** Формування функціональних і нефункціональних вимог до програмної системи

**Проєкт:** Вебзастосунок «CourseHub» — система онлайн-запису на курси

---

## 1. Функціональні вимоги (FR)

Сформульовано 12 функціональних вимог до системи:

| ID | Опис вимоги |
| :--- | :--- |
| **FR-01** | Система повинна надавати студенту можливість переглядати каталог доступних курсів. |
| **FR-02** | Система повинна дозволяти студенту фільтрувати курси за категорією, викладачем та датою початку. |
| **FR-03** | Система повинна дозволяти студенту записатися на курс, якщо є вільні місця. |
| **FR-04** | Система повинна автоматично скасовувати запис студента на курс за його запитом. |
| **FR-05** | Система повинна надсилати студенту email-підтвердження після успішного запису на курс. |
| **FR-06** | Система повинна надавати викладачу можливість переглядати список студентів, записаних на його курс. |
| **FR-07** | Система повинна дозволяти адміністратору створювати, редагувати та видаляти курси. |
| **FR-08** | Система повинна дозволяти адміністратору керувати розкладом занять (додавати/змінювати дати та час). |
| **FR-09** | Система повинна автоматично блокувати можливість запису на курс, якщо кількість місць вичерпана. |
| **FR-10** | Система повинна мати рольову модель доступу (Студент, Викладач, Адміністратор) з різним набором прав. |
| **FR-11** | Система повинна надавати адміністратору можливість експортувати звіт про записи у форматі CSV. |
| **FR-12** | Система повинна дозволяти користувачам відновлювати пароль через email. |

## 2. Нефункціональні вимоги (NFR)

Сформульовано 8 нефункціональних вимог із 6 категорій, кожна має числове значення та спосіб перевірки:

| ID | Категорія | Опис вимоги (з числовим значенням) | Спосіб перевірки |
| :--- | :--- | :--- | :--- |
| **NFR-01** | Продуктивність | Час завантаження сторінки каталогу курсів не повинен перевищувати 1.5 секунди при 100 одночасних користувачах. | Інструмент навантажувального тестування (Apache JMeter). |
| **NFR-02** | Продуктивність | Система повинна обробляти до 500 запитів на запис до курсів на хвилину без помилок. | Стрес-тестування (k6 або Locust). |
| **NFR-03** | Безпека | Паролі користувачів повинні зберігатися в базі даних у вигляді хешу (алгоритм bcrypt). | Перевірка структури бази даних та аудит коду. |
| **NFR-04** | Безпека | Сесія користувача повинна автоматично завершуватися після 30 хвилин неактивності. | Тест-кейс: зачекати 30 хв і спробувати виконати дію. |
| **NFR-05** | Зручність | Процес запису на курс (від відкриття сторінки до підтвердження) повинен займати не більше 3 кліків. | UX-тестування з залученням 5 фокус-користувачів. |
| **NFR-06** | Надійність | Доступність системи (Uptime) повинна становити щонайменше 99.5% на місяць. | Моніторинг серверів (UptimeRobot, Zabbix). |
| **NFR-07** | Супровідність | Покриття коду автоматичними Unit-тестами повинно бути не менше 70%. | Аналіз звіту покриття (Jest, Pytest). |
| **NFR-08** | Сумісність | Інтерфейс повинен коректно відображатися в останніх версіях браузерів Chrome, Firefox, Safari та Edge. | Крос-браузерне тестування (BrowserStack). |

Система повинна формувати звіт про скасовані записи для адміністратора. | **Атомарність** (кілька різних дій в одній вимозі), **Однозначність**. |

## 4. Пріоритизація методом MoSCoW та MVP

* **Must have (Обов'язково) — Входить до MVP:** FR-01, FR-03, FR-07, FR-09, FR-10, NFR-01, NFR-03.
* **Should have (Потрібно):** FR-02, FR-04, FR-05, FR-06, FR-08, NFR-05, NFR-06.
* **Could have (Можливо):** FR-11, NFR-07.
* **Won't have (Не буде зараз):** FR-12, NFR-08.

**MVP (Minimum Viable Product)** — це мінімально життєздатний продукт, який включає вимоги категорії *Must have*.

## 6. Перевірка за чек-листом якості

| Критерій | FR-01 | FR-03 | NFR-01 | NFR-03 | Примітка |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Однозначність** | ✅ | ✅ | ✅ | ✅ | Немає двозначних термінів ("швидко", "багато"). |
| **Повнота** | ✅ | ✅ | ✅ | ✅ | Вказано умови виконання (для NFR є метрики). |
| **Перевірність** | ✅ | ✅ | ✅ | ✅ | Можна написати тест-кейс і перевірити результат. |
| **Несуперечливість** | ✅ | ✅ | ✅ | ✅ | Не конфліктують з іншими вимогами. |
| **Атомарність** | ✅ | ✅ | ✅ | ✅ | Кожна вимога описує лише одну функцію/властивість. |

## 7. Індивідуальне завдання (для двох найважливіших NFR)

**Обрано NFR-01 (Продуктивність) та NFR-03 (Безпека).**

1. **NFR-01 (Продуктивність):**
   * **Спосіб вимірювання:** Використання інструменту **Apache JMeter** для створення сценарію (віртуальні користувачі одночасно заходять на головну сторінку). 
   * **Порогове значення:** 95-й перцентиль часу відповіді не повинен перевищувати 1500 мс.
   * **Наслідки для архітектури:** Потреба у впровадженні **кешування** (наприклад, Redis для кешування списку курсів) та налаштуванні **CDN** для швидкого завантаження статичних файлів (зображень курсів). Можливо, знадобиться оптимізація запитів до бази даних (індексація полів).
2. **NFR-03 (Безпека):**
   * **Спосіб вимірювання:** Аудит коду (Code Review) та перевірка бази даних (наприклад, через SQL-запит `SELECT password FROM users LIMIT 1;`).
   * **Порогове значення:** 100% паролів мають бути захешовані алгоритмом bcrypt із сіллю (довжина хешу 60 символів). Жодного пароля у відкритому тексті.
   * **Наслідки для архітектури:** Обов'язкове використання криптографічних бібліотек на сервері (наприклад, `bcrypt.js` для Node.js або `passlib` для Python). Заборона логування паролів у логи сервера. Впровадження політики складності паролів на рівні валідації.
